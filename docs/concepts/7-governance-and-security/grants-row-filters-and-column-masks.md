# Grants, Row Filters, and Column Masks

**In plain words:** Unity Catalog controls access in layers: GRANT decides who can use a catalog, schema, or table at all; a row filter hides entire rows from a user group; a column mask replaces a sensitive column's value for them. REVOKE takes a grant back. Plain grants have no DENY: access is "nothing unless granted". The newer tag-based policies (ABAC) add DENY policies, in Beta ([ABAC](https://docs.databricks.com/aws/en/data-governance/unity-catalog/abac/), checked 2026-10-11).

**Everyday analogy:** GRANT is the building pass that lets you into the office; a row filter is a shared folder that only shows you your own team's files; a column mask is a redacted line on a shared document that others can't unblur.

**Why real teams use it:** These are Unity Catalog's documented native mechanisms for access control and fine-grained security, evaluated at query time on every read ([docs](https://docs.databricks.com/aws/en/data-governance/unity-catalog/row-and-column-filters), checked 2026-09-27). Grants go to groups, never to people, so a team change is one membership edit. Least privilege means giving a group only the tables its job needs: a schema-wide grant suits engineers, because it covers tables added later, and table-by-table grants suit everyone else, because a new table stays invisible until someone decides to share it. The identity a job runs as must be exempt from masks, or it would read and store `REDACTED` permanently ([ABAC requirements](https://docs.databricks.com/aws/en/data-governance/unity-catalog/abac/requirements), checked 2026-10-11).

**How this repo uses it:** Grants go to groups, never individual users or a `role` (not a documented principal type) ([docs](https://docs.databricks.com/aws/en/data-governance/unity-catalog/manage-privileges/), checked 2026-09-27). See [ADR 0002](../../adr/0002-group-grants-and-native-row-security.md). On the Gold tables there are three groups: `fraud_engineers` (everything), `fraud_reviewers` (alerts and cases with real account names) and `fraud_managers` (closed cases only, account names `REDACTED`). [`sql/50_governance.sql`](../../../sql/50_governance.sql) holds the mask, the row filter and the grants. Both functions exempt engineers and reviewers, and the Gold SQL refuses to run unless the job's identity is in `fraud_engineers`. See [ADR 0011](../../adr/0011-governance-groups-masks-and-external-export.md).

**What was verified:** 2026-09-22, a real spike on `workspace.default`: `GRANT USE CATALOG`/`USE SCHEMA`/`SELECT`, a row filter, and a column mask were all enforced — an excluded row disappeared and a masked column read `REDACTED` (`docs/GAPS.md` G-06). 2026-10-11: custom groups can be created on Free Edition, and a second user can be invited. 2026-10-12: the owner saw all 3,154 cases with 0 `REDACTED` names. A test user in no group was refused at the schema (`does not have USE SCHEMA`). Added to `fraud_managers`, they saw only the 262 closed cases, with every account name `REDACTED`, and the summary view counted 262 for them against 3,154 for the owner, so the filter applies through the view. After `REVOKE SELECT` from the group, their next query was refused (`does not have SELECT on Table`), and a `GRANT` restored it (`docs/GAPS.md` §6).

**Key terms:** GRANT, REVOKE, `USE CATALOG`, row filter, column mask, least privilege, `is_account_group_member()`, run-as identity.
