## 3. Accepted limitations

Items promoted from sections 1–2 that we decided to live with. Each becomes
a bullet in the README's Known Limitations.

| ID | Limitation | Why accepted |
|---|---|---|
| V5 | A line that is not valid JSON (for example truncated) is ingested as **one all-null row**: every column is null, including `_rescued_data`, so the broken text is lost, and the run still succeeds with no warning. Observed 2026-09-24 with a one-line probe file (Bronze grew by exactly 1 row; the row was then deleted) | Bronze stays append-only and complete. The verify query's `null_times` check (expected 0) flags such rows. Since Phase 3, Silver rejects such a row as `missing_id` onto `silver_rejected_transactions`, so it no longer passes silently past Bronze. Capturing the raw text in a corrupt-record column is possible in principle but untested |
| CI-SQL | CI checks the Silver SQL's **structure** (dataset and expectation names, every window frame ending at `1 PRECEDING`, the fixed column lists, the FAIL guards, the pipeline wiring), not its **logic**. There is no Spark in CI | The logic is proven by the workspace runs S2–S5, which matched a pure-Python local calculator (`scripts/expected_silver.py`) row for row. This mirrors validating on a dev target with known data |
| S-ORDER | Two copies of one `transaction_id` with identical arrival keys (`file_arrived_at`, `ingested_at`, `source_file`) would be ranked arbitrarily, so either could become "first" | No current scenario produces it: a re-dropped file always has a different name or arrival time. Recorded so that a future scenario doesn't hit it unnoticed |
| S-RESET | After a Bronze reset, Silver keeps its old results until someone runs **Full refresh all** on the pipeline, because the job task runs without a full refresh | A full refresh on every job run would throw away incremental refresh. The reset notebook prints the 3-step rebuild order (re-ingest Bronze, run the setup SQL, then a full refresh), and `pipelines/README.md` states it |
| S-TARGET | The catalog and schema are set by the bundle variables (`databricks.yml`) at deploy time. Overriding the job's `catalog`/`schema` parameters at **Run now** would move Bronze but not Silver | One bundle variable feeds the job defaults, the pipeline target and the pipeline's Bronze source, so a deploy keeps them together. The job parameter descriptions say to change the bundle variable, not Run now |
| S-HOURS | Features use whole simulated hours: "previous hour" and "last 24 hours" are counted in `step` units, and payments in the same hour are never counted. Hours 1–24 have only partial history (warm-up) | PaySim has hourly time only, so finer windows would be invented. Leaving out the same hour avoids leaking the future. Whether to drop the warm-up hours from training is a Phase 4 decision (G-17) |
| M-RANK | `risk_score` is a ranking, not a calibrated probability: the model is fitted on all fraud plus a 10% sample of non-fraud, with class weights | Alerts are the top 50 per hour, which needs only the order. Calibrating would need an unsampled holdout and adds nothing to a fixed review budget |
| M-BATCH | No real-time scoring: a payment is scored when the ingest job runs after its file lands, not at payment time | Free Edition can't host online feature lookups (online tables unsupported), and the replay is hourly anyway. A serving endpoint plus an online feature store is the production pattern (README Scaling Considerations) |
| M-PROMOTE | Promotion is a manual notebook (`06_promote_model`), not a CI gate, and the challenger isn't shadow-scored | Keeps a person in the loop at this stage. Shadow scoring and drift-triggered retraining are Phase 6 |
| M-SAMPLE | The fit set is sampled (seeded), so a retrain on the same window may pick slightly different non-fraud rows | Fraud is never sampled away, and the comparison and evaluation windows are unsampled, so the reported metrics reflect the real class mix |
